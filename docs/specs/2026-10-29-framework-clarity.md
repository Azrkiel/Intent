# Framework-backed clarity

Approved in the current conversation on 2026-10-29.

Clarity must represent a sufficiently mapped product, rather than six occupied
ledger slots. Before readiness, Intent drafts a framework and independently reviews
it against the current intent. The server owns completeness, freshness, citations,
blockers and the score; models cannot declare the application ready.

The framework covers purpose/users, end-to-end journeys, component boundaries,
data lifecycle, access, failure/recovery, observable acceptance checks, and scope.
Each area has named aspects, cited statements, and clearly labeled implementation
proposals. A small local tool does not need invented accounts, servers, integrations
or scale. The reviewer checks specificity, internal consistency, success/failure
paths, all confirmed requirements, and unsupported commitments. Missing information
that needs a user decision produces an actionable question; a defective map is
retried through analysis rather than silently accepted.

Every new utterance or analysis attempt invalidates the previous review. A review
is bound to the requirements revision and ledger content. Failed/partial passes,
omitted review addresses, invalid citations and unresolved critical decisions keep
the gate closed. User approval remains required after a complete map and playback.
The framework accompanies the brief and the later phase planner as explicitly
reviewed proposal context, without converting proposals into confirmed requirements.

The workspace shows review status, missing work and an expandable framework.
Demo mode remains scripted and labeled; it must not claim live model reasoning.
Legacy live sessions without a framework must be reanalyzed before new approvals,
compilation, planning or builds. Existing historical artifacts remain readable.

Tests must prove that vague slot coverage, missing areas, missing citations,
incomplete semantic review, failures, and stale maps cannot open the live gate.
Concrete complete maps can pass; minor implementation proposals can remain labeled.
Offline tests establish orchestration behavior, not live model quality.
