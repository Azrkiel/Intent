## 8. Decisions, rationale, and invariants

- Requirements approval, plan approval, permission approval and phase acceptance
  remain separate. Identity includes plan ID/revision/hash and requirements revision.
- Worker completion means `verifying`; only inspected/staged output becomes
  `integrated`. Neither means phase acceptance.
- One active phase; default one worker, configurable at most two. Claims precede
  filesystem/model side effects and remain transactional across executor instances.
- Dependents start from integrated staging commits, never unreviewed worker trees.
  Successor phase launch must remain explicit even after acceptance.
- Preserve cancelled, stale, failed and uncertain work. Never reset/reuse the Intent
  source checkout as a generated project or discard unreviewed worktrees.
- Persist integration intent before publishing staging refs. Unknown external
  outcomes block; never infer success or silently replay dispatch/promotion.
- Trusted policy `git-inspection-only-v1` supports only proposed argv
  `["git", "diff", "--check"]`, resolved against saved base/snapshot. Arbitrary
  project tests, scripts and installs have no approved sandbox runner.
- Git commands use sanitized environment, disabled hooks/external diff, long-path
  support, deadlines/output limits, and restrictive metadata checks. Do not weaken
  these to make a generated task pass.
- Worker summaries/test edits are claims/changed code. Git inspection does not
  establish application correctness or semantic compliance with textual exclusions.
- Keep default runtime on loopback; no account authentication exists. Keep keys,
  session data, generated apps and reports ignored under `.data/`.
- No live qualification, billing change, account rotation, provider fallback or
  multiple-account inference has been established by these simulations.
