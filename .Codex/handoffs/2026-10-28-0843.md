#### 8.1 Node hierarchy and the central root

```text
 [Phase P1] <--------- contains -------- [PROJECT ROOT] -------- contains --------> [Phase P2]
      |                                Intent + direction                              |
      |                                Global scope/rules                              |
      |                                Orchestration + gates                           |
      v                                      |                                        v
 [Project P1-W1]                              |                                  [Project P2-W1]
 scope + packet                              |                                  scope + packet
      |                             Global screen contracts                            |
      v                                                                               v
 [Ordered leaf tasks]                                                        [Ordered leaf tasks]

 Dashed depends_on edges: scheduling / interface obligations only.
 Solid contains edges: the single-parent ancestry used for worker context.
```

The root is the overall project. A child "project" or "subproject" is the existing
work package (`P1-W1` etc.), which remains the dispatch unit; leaf tasks remain
ordered work within that scope. Phase nodes provide grouping, shared contracts,
and review gates. This naming does not create independent repositories or new
recursive scheduler units. Current bounded phase -> package -> leaf structure stays.

| Node/body | Required contents |
| --- | --- |
| Project root, centered in initial/recentered view | Vision, user intent, journeys, cited requirements, overall scope/exclusions, proposed and unresolved choices, global architecture and screen contracts; phase/package dependency overview, orchestration order, eligibility rules, worker limits, review/stop gates |
| Phase | Goal, position in delivery order, phase prerequisites, shared interface contracts, phase acceptance boundary, happy/failure flow; child IDs and high-level summaries, never nested child packets in worker context |
| Subproject/work package | Goal and why it exists, exact scope, exclusions, owned paths, dependencies, consumed/produced interfaces and versions, inputs, outputs, preconditions, steps, acceptance, trusted-check status, artifacts, unresolved choices, handoff requirements |
| Leaf task | Ordered steps, cited acceptance, exact proposed command argv and expected results, artifacts, owner/package link; displayed status distinguishes model claims from trusted evidence |
| Screen attachment | Purpose, all declared empty/loading/error/success states, wireframes, citations, related work where explicitly known; global design contract owned above the implementation branches |

#### 8.3 Worker reads: ancestors plus assigned scope

Define `ancestor-context-v1` as application-owned instruction policy. A package
worker reads, in order: root shared context -> its phase context -> its assigned
project packet -> the ordered leaves within that assigned project. If individual
leaf assignment is introduced later, its allowed scope becomes its own ancestor
chain and leaf; sibling leaves are not automatically included.

The worker may not fetch or receive sibling/cousin project bodies, other phases'
implementation packets, unrelated node handoffs, the full graph, or full plan
export. Names/IDs in an ancestor's high-level orchestration overview do not grant
access to the bodies they identify. Dependencies are not ancestry.

Proposed `WorkerContextManifest` fields:

- Source plan approval identity; assigned canonical package ID and task IDs.
- Ordered ancestor node IDs and per-body hashes; explicit readable node/doc IDs.
- Global intent/requirements/design contracts, phase contract, and complete local
  package scope; all ancestor bodies are flat projections without descendant bodies.
- Applicable source quotes/citations, normalized owned write paths, forbidden
  scope expansion, interface versions, and published input artifact hashes/commits.
- `context_policy_version`, context schema version, deterministic context hash,
  expected outputs, stop conditions, and required handoff fields.

Build the manifest server-side from validated data, never from a browser/model
supplied allowlist. Preserve exact source quotes and argv arrays. Measure serialized
size before dispatch; block an oversized or incomplete context rather than silently
truncating requirements, broadening reads, or dropping provenance.

The current Codex worker has a normal project checkout and file tools. Restricted
packet construction and node/document access can be enforced by the orchestrator;
a prompt alone does not create filesystem read isolation. Existing source checkouts
may contain sibling implementation files. Do not claim hard read isolation unless
a separately qualified sandbox/tool policy enforces it. Write ownership verification
and existing profile/sandbox controls remain mandatory and distinct.

#### 8.4 Cross-branch interfaces without sibling instructions

For a dependency between projects A and B, define the interface at their nearest
shared ancestor. The orchestrator publishes a narrowly scoped contract/handoff
snapshot there: interface name/version, allowed inputs/outputs, artifact hashes,
producer provenance, integration commit, evidence state, and remaining decisions.
B consumes that ancestor snapshot; it does not read A's task body or private work log.

Only the orchestrator publishes these snapshots after the applicable existing
dependency/check gate. Mark verified/integrated artifacts separately from human
phase acceptance; do not relabel a same-phase integrated prerequisite as accepted
by the human. A missing, incompatible, stale, or unpublished contract blocks B.
Changes pin a new context hash before a future dispatch; do not mutate an active
worker's input silently. Never resolve a missing contract by opening sibling context.

Global screen/wireframe specifications belong to the root's shared design contract
and can be projected as screen attachments in the human graph. They are not sibling
implementation handoffs. Local screen bindings must be explicit and validated if
added later; do not guess authoritative ownership from titles or citation overlap.
